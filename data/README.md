# JFR Ranch Dashboard — dev.sqlite

`dev.sqlite` is a development database built entirely from **real** JFR
Ranch data — no synthetic or fabricated rows anywhere in this file. It is
generated by `web/scripts/build_dev_db.py`, which is idempotent (safe to
re-run; every table is dropped and recreated from the source files each
time).

This file is a stand-in for a future live Postgres connection. The
app-native tables (Part 2 below) keep the **exact same table and column
names** as the client's own Supabase cattle-app project (a *different*
Supabase project from Part 1b), so a future sync job can point at that
project instead of this SQLite file with minimal code changes.

There are three families of tables — **do not conflate them**:

- **`gl_*` tables** — derived from the CenterPoint General Ledger /
  accounting pipeline ("Unit Economics Reporting" Excel project). These
  carry real **dollar** figures.
- **`master_lot_schedule` / `master_crop_schedule`** — the unified lot /
  crop-lot dimension tables (see
  `../docs/PROMPT - Master Schedule Unification.md`), pulled live from
  JFR's own Supabase project every time this file is rebuilt.
- **App-native tables (no prefix)** — copied verbatim from a snapshot of
  the client's own (separate) Supabase cattle-management app. These carry
  real **head counts, weights, dates, market quotes, and hedge
  positions**.
- **`lot_crosswalk`** bridges `master_lot_schedule` and the app-native
  tables, because the two systems do **not** share lot identity (see
  Caveat 2 below — read it before writing any query that joins across the
  two families).

### Part 1b — `master_lot_schedule` / `master_crop_schedule` (source: Supabase, live)

As of 2026-09-22, these two tables retire the old `gl_lot_summary`,
`gl_lot_master`, `gl_master_lot_schedule`, and `lot_attrs_app_cohort`
tables (see `../docs/PROMPT - Master Schedule Unification.md` for the full
history). They are no longer read from a local Excel/CSV file — the Excel
project's `supabase_sync.py` writes them to Supabase once its own
Reconciliation is clean, and `build_dev_db.py` reads them straight back
via a plain PostgREST GET (see "Regenerating this database" below for the
credentials this needs).

| Table | Grain | Rows |
|---|---|---|
| `master_lot_schedule` | One row per GL lot (primary key = `lot`) — GL-computed metrics plus app-derived ADG/weight plus client-editable fields, all on one row | 35 |
| `master_crop_schedule` | One row per crop lot (primary key = `crop_lot`) | 34 |

Notes on these tables:

- `gl_transactions.lot` uses the **GL lot label** (e.g. `"37-X"`,
  `"July 26 Feeders"`), not the app's `lot_number`. See Caveat 2.
- `gl_transactions.txn_number` is a mixed-type column in the source (some
  rows have a numeric txn ID, some have a free-text label like `"Rsd Hfrs
  to Cow Herd"`, and a small number even have a raw date value in that
  cell in the source ledger export). It is stored as `TEXT` here so all
  three forms round-trip cleanly; don't assume it's numeric.
- `gl_transactions.group_name` is named that (not `group`) because
  `GROUP` is a reserved SQL keyword — it maps to the source column named
  simply `Group`.
- `master_lot_schedule.lot` is unique by construction (Postgres primary
  key on the Supabase side — see the Excel project's
  `Guide - Supabase Setup for JFR Sync.md`).
- `gl_account_map`'s header row was verified by scanning for the row
  whose first cell is literally `"Acct"` (found at row 4 of the sheet;
  rows 1–3 are title/notes). The build script detects this dynamically
  rather than hardcoding the row number, in case a future export shifts
  it.
- All Excel dates are stored as ISO `YYYY-MM-DD` text, not Excel
  datetime/serial values.

## Critical caveats — read before writing any query

1. **`lots.is_test`** — 3 of the app's 12 lots are test data
   (`TEST_DOC1`, `TEST_DOC2`, `Test-1`). Any query against `lots` (or a
   join through it) must filter `is_test = 0` unless you are explicitly
   auditing test data.

2. **GL lot identity ≠ app lot identity.** `master_lot_schedule.lot` /
   `gl_transactions.lot` (e.g. `"37-X"`) and the Supabase app's
   `lots.lot_number` (e.g. `"37X"`, `"37X-1"`, `"37X-F"`) are DIFFERENT
   grains — never join them directly on text equality. Always go through
   `lot_crosswalk`. Some app sub-lots roll up many-to-one into a single
   GL lot (`match_type = 'rollup'`); some GL lots have no app presence at
   all (`match_type = 'gl_only'`) and must keep using
   `master_lot_schedule`'s own columns for head/weight data instead of
   the app tables; a few are `match_type = 'suspect'` matches needing
   human confirmation (currently: `FEEDPEN-27`, flagged as possibly the
   same as GL's `Feed Pen-25` but with mismatched years) — never treat a
   `suspect` row as a confirmed match. Rows with `decision_needed = 'YES'`
   have not been signed off by a human yet.

3. **`market_quotes.created_at`** is uniformly a single backfill
   timestamp (2026-09-10) — never use it for recency. Always use
   `quote_date` (which ranges 2025-12-31 through 2026-09-10 in this
   snapshot).

4. **Death Loss is already its own GL cost line.** The GL nets Death Loss
   (account `623000`, `Death Loss Expense`) as its own real cost line,
   already separate from Purchased Cattle at entry cost. Never add death
   loss on top of purchase cost as an extra charge — it's already a
   distinct `Report Line` value in `gl_transactions`.

5. **`lots.total_cost_in` is never relieved when head are sold.** It's a
   whole-lot cumulative purchase cost. Dividing it by remaining head
   count for a mostly-sold lot produces absurd numbers (e.g.
   $200k+/head). Never present `total_cost_in / head_current` (or
   similar) as a real per-head remaining cost without clearly labeling it
   an approximation.

6. **Cost of Gain has three legitimate, very different definitions** —
   feed-only (≈ $0.37–0.49/lb), operating (≈ $0.66–1.24/lb), and all-in
   (≈ $1.00–1.50/lb). This database does not compute Cost of Gain itself
   (that's the app's job, built from `gl_transactions` + `gl_head_days` +
   ADG data) — but flag this clearly for whoever builds those queries
   next, and always label which definition a displayed number uses.

7. **"Grazing - Summer Native" is booked at $0 for every 2026 lot** in
   this snapshot (`SUM(amount) = 0` for `report_line = 'Grazing - Summer
   Native' AND production_year = 2026`, verified in this build). This is
   a real gap in the accounting, not a bug in this import — feed cost of
   gain for 2026 lots is understated as a result.

8. **`positions` currently contains only 3 rows**, and each one's own
   `notes` field explicitly labels it as a verification/test row (e.g.
   `"[VERIFICATION ROW 2026-09-10 - not a real position; delete when done
   looking]"`), not a real hedge position. Don't present hedge coverage
   (including `hedge_coverage_by_month`, which is derived from
   `positions`) as real until real rows replace these.

None of the above gaps were fixed, backfilled, or papered over in this
import — the point of this section is honesty about known gaps in the
source data as it exists today, 2026-09-18.

## Regenerating this database

```
cd web
python scripts/build_dev_db.py
```

The script reads directly from the Box-synced source files (Unit
Economics Reporting workbook + Account Map, `ranch.sqlite`, and the
crosswalk CSV), plus a live read from Supabase for `master_lot_schedule`/
`master_crop_schedule`, and writes `web/data/dev.sqlite` from scratch
every time. It never modifies any source file or Supabase table (writes
to Supabase are `Unit Economics Reporting/supabase_sync.py`'s job, not
this script's).

The Supabase read needs `JFR_SUPABASE_URL` / `JFR_SUPABASE_SECRET_KEY` —
put them in `web/.env.local`, or leave them unset there and the script
will fall back to reading them from
`Unit Economics Reporting/.env` (same Supabase project, already set up —
see that project's `Guide - Supabase Setup for JFR Sync.md`).
